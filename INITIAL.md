## FEATURE 11 — Префиксы департаментов в имени файла → роли → курсы (ПРИОРИТЕТ)

**Источник:** встреча с Дмитрием 29.07.2026 (транскрипт
`data/referance/29.07.2029 Встреча с дмитрием.txt`). Клиент отказывается от
ролевых папок (№1, блок `folders` в roles.json так и остался пустым) в пользу
ОДНОЙ плоской папки с аббревиатурами департаментов в начале имени файла.
Мотив — наша же ловушка №1: копии документа по ролевым папкам расходятся при
правке. Живая тестовая папка **«Регламент_тест2» (id 4760370)**, подпапка
`MONITOR_FOLDER_ID=4698010`, реальный формат имён (проверено через
`disk.folder.getchildren`):

```
FO Внешний вид сотрудника.docx
ENG ДЕЙСТВИЯ ДЕЖУРНОГО СМЕНЫ ИНЖЕНЕРНОЙ СЛУЖБЫ ПРИ СРАБОТКЕ....docx
ALL КОНФЕДЕНЦИАЛЬНОСТЬ.docx
FO, HSKP, ENG, RES Вывод номера из обращения (ремонт, OOS, ООО).docx
FO, RES, SAL Негарантированные бронирования.docx
FO, RES АЛГОРИТМ БРОНИРОВАНИЯ ПО ТЕЛЕФОНУ.docx
```

Формат де-факто: **латинские аббревиатуры через запятую+пробел до названия**,
`ALL` = все сотрудники. Аббревиатуры: FO (СПиР), HSKP (хаускипинг),
ENG (инженерная служба), RES (бронирование), SAL (продажи), ALL; Дмитрий
обещал ещё FIN и «и так далее» — реестр должен расширяться конфигом.

**Цель фичи — ПОЛНАЯ цепочка:** префикс файла → роли документа → (а) какие
курсы назначаются сотруднику его роли, (б) по каким стандартам бот отвечает.
Сегодня работает только (б)-половина: `role_mask` фильтрует RAG-выдачу
(`app/roles.py:45`), но роли чанков неоткуда взяться (folders пуст), а курс
назначается ВСЕМ одинаково — первый активный `courses[0]`
(`state_machine.py:58,95`), к роли не привязан вовсе.

### Что сделать

1. **Реестр префиксов** в `data/roles.json`, новый блок:
   ```json
   "prefixes": {
     "FO": "admin_reception", "HSKP": "housekeeper", "ENG": "engineer",
     "RES": "reservations", "SAL": "sales", "FIN": "finance",
     "ALL": "all_staff"
   }
   ```
   плюс три НОВЫЕ роли в `roles`: `reservations` «Отдел бронирования»,
   `sales` «Отдел продаж», `finance` «Финансовый отдел». Существующие
   role_id не трогать — индекс уже хранит их (бэкфилл 842 чанков).
   Эти же role_id лягут в блок `departments` №8 — единый реестр.

2. **Парсер префиксов** (чистая функция, `app/roles.py`):
   `roles_from_filename("FO, RES АЛГОРИТМ....docx") → ["admin_reception",
   "reservations"]`. Правила: от начала имени берутся токены через запятую,
   пока токен (upper, strip) есть в `prefixes`; первый не-префиксный токен —
   начало названия. Нет ни одного известного префикса → `None` (не пустой
   список — различать «без префиксов» и «ALL»).

3. **Ингест**: в поллере файлов и disk-вебхуке роли документа =
   `roles_from_filename(file_name)`, при `None` — фолбэк на текущую логику
   (роли папки из `folders` → `all_staff`). Плюс **фильтр мусора ДО
   парсера**: скип файлов, чьё имя начинается с `.` или `._`
   (`.DS_Store`, AppleDouble `._*.docx` — лежат в живой папке ПРЯМО СЕЙЧАС,
   `._*.docx` = бинарь с расширением docx, парсер съест мусор в индекс).

4. **Назначение курса по роли** — главное изменение FSM. Роли курса НЕ
   хранить в схеме: считать на лету `roles_from_filename(course["doc_name"])`
   (doc_name уже в courses; старые курсы без префикса → None → all_staff →
   видны всем = сегодняшнее поведение, обратная совместимость бесплатно).
   Порядок определения инвертируется: сейчас сессия создаётся с
   `courses[0]`, ПОТОМ ROLE_SELECT — надо: сначала роль (из №8 или меню),
   потом курс = первый активный, чьи роли пересекаются с
   `{роль сотрудника, all_staff}`. Подходящих нет → «для твоей роли пока
   нет курсов» (+ уведомить HR?). Техдеталь: `create_session` требует
   course_id — либо разрешить NULL миграцией, либо назначать курс в
   `_handle_role_select` через `update_session(course_id=...)`.

5. **Ответы бота** — менять нечего: `role_mask` уже фильтрует по ролям
   чанков; префиксы просто начинают их наполнять. Смена роли командой
   «Роль» остаётся (страховка).

### Ловушки

- **`doc_name` = ключ идентичности** (index_store-матчинг, courses,
  удаление two-strike, №4). Префикс из doc_name НЕ вырезать — хранить имя
  файла как есть; чистое название без префикса — только для отображения
  сотруднику (отдельный helper `display_name()`).
- Опечатки клиента неизбежны (в живой папке «КОНФЕДЕНЦИАЛЬНОСТЬ») —
  неизвестная аббревиатура в начале имени молча уйдёт в «начало названия»,
  документ станет all_staff. Минимум — лог; лучше — уведомление HR
  «файл X: неизвестный префикс Y» (решить в PRP).
- Нормализация: `FO,RES` без пробела, `fo` в нижнем регистре — парсер
  обязан переварить (upper + strip на каждом токене).
- Очерёдность курсов при нескольких подходящих: ALL-курсы первыми или
  ролевые? — **вопрос Дмитрию/HR**, пока: порядок активации (как сегодня).
- Корень 4698010 захламлён нестандартами (договор Aiso, ТЗ, объём рынка) —
  индексируются как all_staff и загрязняют выдачу. Поднять с Дмитрием
  вопрос чистоты папки / переключить MONITOR_FOLDER_ID на «Регламент_тест2»
  после утверждения структуры.
- `audience guest` префиксами не покрыт — гостевая логика №1 не меняется.

## FEATURE 7 — Кнопки вместо буквенных ответов

**Запрос Дмитрия:** сотрудники будут путать раскладку (латинские A/B/C/D vs
кириллические А/В/С/Д) — сделать кнопки, как в Telegram-ботах.
Проблема реальная: в №3 уже пришлось нормализовать кириллицу от HR
(`hr_tools._norm_letter`). Кнопки убирают этот класс ошибок полностью.

**Возможность подтверждена:** чат-боты Bitrix умеют «клавиатуры, вложения и
другие элементы интерфейса» (`data/referance/bitrix24_docs.md:1370`). Но
детальной статьи по параметру `KEYBOARD` в 51k-строчной выжимке НЕТ —
структуру кнопки (TEXT / COMMAND / COMMAND_PARAMS / BG_COLOR / DISPLAY)
брать из онлайн-доков и проверять живьём ДО написания кода.

### Что сделать

1. **Кнопки в сообщениях бота** — параметр `KEYBOARD` в существующих вызовах
   `imbot.message.add` (`_send` в `bitrix_bot.py`; `notify_hr` в
   `state_machine.py:335` без кнопок — кроме одного места ниже). Точки:
   - вопросы тестов (basic/exam): кнопки `A`–`D` с текстами вариантов;
   - READING-меню: «Далее», «Тест», «Вопрос» (вопрос всё равно текстом — кнопка
     только подсказывает команду);
   - выбор роли (если №8 оставит fallback-меню): кнопки `1`–`N`;
   - HR «Допустить {id}» в уведомлении о завершении базового теста —
     кнопка «✅ Допустить» (это сообщение идёт через `notify_hr` — сюда
     кнопку добавить точечно, отдельным параметром).

2. **КЛЮЧЕВОЙ дизайн-вопрос — как приходит нажатие.** ОТВЕТ НАЙДЕН (доки,
   10.08): вариант (а) в Bitrix ОТСУТСТВУЕТ — нажатие COMMAND-кнопки приходит
   событием `ONIMCOMMANDADD`, команда должна быть зарегистрирована
   `imbot.command.register`. Реализуется вариант (б): COMMAND_PARAMS несёт
   ровно те payload'ы, которые FSM уже ждёт («A», «2», «Готов»), обработчик
   прокидывает их в process_message. Постоянной reply-клавиатуры (как в TG)
   нет — только инлайн-кнопки при сообщении (лимит 30КБ, KEYBOARD_OVERSIZE);
   убрать/заменить кнопки — imbot.message.update. Живьём проверить формат
   события ДО кода. Исторический план двух вариантов:
   - (а) кнопка шлёт обычное текстовое сообщение от имени юзера → прилетает
     тем же `ONIMBOTMESSAGEADD` в `/handler` → **FSM не меняется вообще**,
     кнопка просто «печатает за юзера» ровно тот payload, который FSM уже
     ждёт («A», «2», «Далее»). Идеальный вариант — добиваться его.
   - (б) кнопка шлёт COMMAND → нужно событие `ONIMCOMMANDADD` (регистрация
     команд `imbot.command.register`), новый разбор в `/handler`, маппинг
     command → тот же `process_message`. Дороже, но payload-ы держать теми
     же текстами, чтобы FSM остался нетронутым.

3. **Текстовый ввод ОСТАЁТСЯ.** Кнопки — сверху, не вместо: RAG-вопросы в
   READING всё равно свободным текстом; ответ «A» с клавиатуры должен
   работать как раньше (регресс недопустим). Нормализацию кириллицы НЕ
   выпиливать.

### Ловушки

- `_recent_msgs`-дедуп в `bitrix_bot.py`: два нажатия кнопки подряд с
  одинаковым payload — проверить, что дедуп не съест легитимный повтор
  (окно по message_id или по тексту? проверить).
- Старые сообщения с кнопками остаются в чате: юзер может нажать «B» на
  ВЧЕРАШНЕМ вопросе. FSM это переживает (ответ упадёт в текущий вопрос) —
  но зафиксировать поведение осознанно; при варианте (б) можно передавать
  `COMMAND_PARAMS` с q_idx и отбрасывать протухшие.
- Мобильный клиент Bitrix: рендер клавиатур проверить на телефоне —
  сотрудники отеля сидят с телефонов.

### Что сказать клиенту

Кнопки доступны уже сейчас (не «при развитии платформы») — это доработка
обработки, а не ожидание фичи Bitrix.

## FEATURE 8 — Роль из профиля Bitrix (не вручную)

**Запрос Дмитрия:** роль не должна вводиться текстом — подтягивать из
профиля. **Текущее состояние:** роль выбирается ЦИФРОЙ из текстового меню
(`state_machine._start_role_select` / `_handle_role_select`,
`app/state_machine.py:110-138`), из профиля НЕ подтягивается — доработка
нужна.

### Что сделать

1. **Маппинг «отдел → роль»** в `data/roles.json`, новый блок:
   ```json
   "departments": { "<dep_id>": "housekeeper", ... }
   ```
   По образцу блока `folders` (folder_id → роль). `UF_DEPARTMENT` юзера мы
   УЖЕ получаем и храним: поллер отделов пишет в `seen_portal_users.departments`
   (`bitrix_bot._departments_json`, `db.py:87`). Должность (`WORK_POSITION`)
   как источник НЕ брать — свободный текст, на портале бывает пустым
   (в выжимке доков встречается `"WORK_POSITION": ""`); отдел структурирован.

2. **Автоопределение при старте онбординга** (`start_onboarding` и ветка
   нового юзера в `process_message`): uid → отделы (из `seen_portal_users`,
   при промахе — живой `user.get`) → маппинг → если роль найдена однозначно,
   сессия создаётся сразу в READING с этой ролью, сотруднику сообщение
   «Твоя роль: {label} (из профиля)». Меню НЕ показывается.

3. **Fallback = текущее меню.** Нет маппинга / отдел не в `departments` /
   юзер в двух отделах с РАЗНЫМИ ролями → показать существующий ROLE_SELECT.
   Ничего не ломаем: пустой блок `departments` = поведение как сегодня
   (тот же принцип, что пустой `folders` в №1).

4. **Команда «Роль» в READING остаётся** — ручная смена роли для
   тестирования (`state_machine.py:159`) и страховка от кривого маппинга.

### Ловушки

- `UF_DEPARTMENT` — массив (юзер в нескольких отделах). Однозначность:
  все отделы юзера мапятся в ОДНУ роль → берём её; в разные → fallback-меню.
- `seen_portal_users.departments` заполнен только для отделов из
  `WATCH_DEPARTMENT_IDS` — сотрудник вне отслеживаемых отделов там без
  департаментов или отсутствует → живой `user.get` (скоуп `user` уже нужен
  по №2).
- dep_id в `roles.json` — строки или int: `_departments_json` сортирует
  int-ы, JSON-ключи всегда строки. Нормализовать в одном месте.
- Заполнить `departments` реальными ID — у клиента (как folder_id в №1,
  который ДО СИХ ПОР не заполнен — та же зависимость от клиента, напомнить).

## FEATURE 9 — Пересдача + эскалация руководителю (СКОУП УТОЧНЁН 2026-07-24)

**Запрос Дмитрия:** о непрохождении тестов информировать руководителя,
с эскалацией. **Текущее состояние:** при «❌ Не сдан» уведомление уходит
ТОЛЬКО HR (`state_machine._finish_phase`, `notify_hr`,
`app/state_machine.py:261`); пересдачи как механизма нет (DONE финален).

**Решения Никиты (24-07):**
- порог сдачи ОСТАЁТСЯ 70% (`round(total*0.7)`); не сдал → пересдача доступна;
- руководители задаются ВРУЧНУЮ по email (реестр), НЕ через
  `department.get`/`UF_HEAD` — этот путь из старой версии фичи ОТМЕНЁН;
  HR может добавлять/удалять/смотреть; сид: `n.sharapov@proptech.digital`
  (временный, потом заменят);
- канал доставки ПОКА чат Bitrix (email-рассылка — позже, SMTP-кредов нет);
  email в реестре → uid через `user.get` (тот же паттерн, что «Пригласить»);
- единственный триггер эскалации: **7 дней после назначения курса, экзамен
  не сдан** — неважно, провалил или даже не начинал («статус не пройден +
  7 дней»). Мгновенной эскалации при провале НЕТ; напоминаний сотруднику
  НЕТ (единственная нотификация сотруднику — при самом назначении, уже есть).

### Что сделать

1. **Пересдача экзамена.** При «❌ Не сдан» бот предлагает: «Напиши
   *Пересдать* — и пройди экзамен ещё раз». Команда «Пересдать» в DONE-сессии
   с несданным экзаменом → сессия обратно в EXAM, `q_idx=0`, старые
   exam-ответы этой сессии удаляются из `answers` (иначе
   `get_session_answers` в `_finish_phase` посчитает ОБЕ попытки —
   `correct_count` будет кривой). Попытки не ограничены (допущение — лимита
   клиент не задавал). Базовый тест не пересдаётся (гейт HR «Допустить»
   как был).

2. **Реестр руководителей** — таблица `managers` (email PK, added_by,
   added_at), сид `n.sharapov@proptech.digital` при миграции. HR-команды
   (в HR-боте, за существующим гейтом /hr, по образцу «Пригласить»):
   - «Руководители» — список;
   - «Руководитель добавить {email}» / «Руководитель удалить {email}».
   Обновить help-текст HR (ветка `else`).

3. **Эскалационный луп** — ежечасный, по образцу `_weekly_rating_loop`
   (№5): выбрать сессии старше 7 дней (`started_at`), где экзамен не сдан
   (state != DONE, ИЛИ DONE и score_exam < порога), эскалация ещё не
   отправлена → всем руководителям из `managers`:
   «⚠️ {ФИО/email} не прошёл(а) обучение по курсу "{doc_name}" за 7 дней
   (статус: {не начал / базовый тест / ждёт допуска / экзамен не сдан N/M})».
   Доставка: email руководителя → uid (`user.get`, как в «Пригласить») →
   `imbot.message.add` паттерном `notify_hr` (CLIENT_ID + retry) — вынести
   общий `_send_to_user(uid, message)` вместо копипасты.
   Идемпотентность: одна эскалация на (user_id, course_id) — таблица
   `escalations` (user_id, course_id, notified_at) или отметка в сессии;
   повторов нет (допущение — клиент повторы не просил).

### Ловушки

- **Пересдача сбрасывает exam-ответы** → «История {email}» (№3) и лист
  «Детали» (№10) теряют прошлую попытку. Осознанно: храним только
  последнюю. Если жалко — attempt-колонка в answers, но это дороже;
  решить в PRP (дефолт: удалять).
- После пересдачи сессия снова DONE → эскалационный луп должен смотреть
  СВЕЖИЙ score_exam; пересдал вовремя — эскалация не шлётся; уже
  отправленная эскалация не «отзывается» (руководителю можно слать
  «✅ пересдал» — НЕ делаем, клиент не просил).
