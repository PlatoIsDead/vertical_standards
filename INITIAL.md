## FEATURE 2 — Доступ по email и автостарт (22 ч / 44 000 ₽)

1. **HR работает по email, не по Bitrix-ID.**
   - Новая HR-команда «Пригласить {email}»: бот ищет сотрудника через
     `user.get` с `FILTER[EMAIL]` (метод подтверждён в выжимке доков), сохраняет
     в новую таблицу `employees` (bitrix_uid PK, email, full_name, status
     invited/active, added_by, added_at) и **сам пишет сотруднику первым**
     (`imbot.message.add`, `DIALOG_ID=u{uid}`) — создаёт сессию в ROLE_SELECT
     и шлёт меню выбора роли. Диалог начинается без первого сообщения сотрудника.
   - Существующая команда «Допустить …» принимает и email, и ID (обратная
     совместимость: цифры = ID, есть @ = email).

2. **Whitelist.** `process_message`: пользователь не в `employees` → вежливый
   отказ «Обратитесь к HR». Это закрывает открытый вопрос №2 из planning.md
   (сейчас курс может начать ЛЮБОЙ пользователь портала). Legacy-сессии
   (созданные до whitelist) не ломать — засеять `employees` из
   `sessions.user_id` при миграции.

3. **Ловля новых сотрудников — два пути (оба лишь УВЕДОМЛЯЮТ HR, автостарт
   только после «Пригласить»: доступ — только у одобренных):**
   - `OnUserAdd`: событие в 51k-строчной выжимке доков ОТСУТСТВУЕТ (как и
     OnDiskFileAdd — см. planning.md) — вероятно, доступно только OAuth-приложению
     через `event.bind`, не простому вебхуку. Сделать endpoint `/user-webhook`
     (по образцу `/disk-webhook` — он уже есть и ждёт событher), регистрацию
     event.bind — задокументировать; живая проверка на сервере.
   - **Основной механизм — периодический опрос отдела** (для переводов между
     отделами события в Bitrix нет вовсе): `user.get` с `FILTER[UF_DEPARTMENT]`
     по списку отделов из .env (`WATCH_DEPARTMENT_IDS=1,2`), период как у
     дисκ-поллера; diff со списком известных uid (таблица) → HR-уведомление
     «Новый сотрудник {ФИО} ({email}). Пригласить: Пригласить {email}».

## FEATURE 3 — Инструменты HR (20 ч / 40 000 ₽)

1. **Правка тестов через чат.** «Изменить {N курса} {номер вопроса 1–15}» —
   бот показывает текущий вопрос и шаблон замены; HR шлёт замену одним
   сообщением (текст, 4 варианта A–D, «Ответ: X»). Нумерация из сметы:
   1–5 = базовый тест, 6–15 = экзамен. Валидация — переиспользовать
   `course_generator._validate_questions` (поштучно). Только замена 1:1,
   количество вопросов не меняется (сессии хранят `current_q_idx` — сдвиг
   индексов сломал бы сотрудников в середине теста).
   - HR-хэндлер сейчас stateless if/elif — для двухшаговой правки нужно
     состояние HR-диалога (минимально: in-memory dict `{hr_user_id: pending_edit}`
     с TTL; БД не обязательна — потеря состояния при рестарте = HR повторит команду).
2. **«История {email}»** — вопросы и ответы сотрудника: email → uid через
   `employees` (№2), сессии + `answers` (`get_session_answers`), тексты вопросов
   по `question_id` = индекс в `questions_json` курса.
3. **«Отчёт»** — кто прошёл обучение и с каким результатом: по `sessions`
   (state, score_basic/score_exam, даты) + ФИО/email из `employees`;
   для legacy-сессий без записи в employees показывать голый user_id.
4. Обновить help-текст HR-бота (ветка `else`) — там перечислены все команды.

## FEATURE 4 — Расширение загрузки документов (22 ч / 44 000 ₽)

1. **Вложенные папки.** `_check_folder` рекурсивно обходит подпапки
   (`disk.folder.getchildren` без `filter TYPE=file` отдаёт и папки; сейчас
   фильтр режет до файлов). Роли наследуются от корневой ролевой папки;
   если подпапка сама есть в `roles.json` — её маппинг главнее. Ограничить
   глубину (например, 5) — защита от неожиданных структур.
2. **Новые форматы: PPTX и TXT** (+PDF дёшево через pypdf — в planning.md он
   есть, в тексте сметы клиенту нет: уточнить, делать ли). PPTX: python-pptx,
   чанк = слайд(ы), heading = заголовок слайда. TXT: сплит по 400–500 слов
   (как чанкер MVP), heading = имя файла. Расширить фильтр `("docx", "md")`
   в двух местах: `_check_folder` и `process_new_document`.
3. **Отправка файла в чат** (`im.disk.file.commit` / `im.disk.file.save`,
   строки ~1826–1834 выжимки): в `_start_reading` прикладывать сам документ,
   а не только `detail_url`. Ловушка: методы `im.disk.*` работают с CHAT_ID,
   а у нас DIALOG_ID вида `u123` — нужен маппинг (im.dialog.get или chat из
   события); исследовать в выжимке на этапе PRP, при неудаче — оставить ссылку
   (graceful fallback).
4. **Замена версии по имени файла.** КЛЮЧЕВАЯ ЛОВУШКА — конфликт с дедупом №1:
   сейчас повторное имя = «копия для другой роли» (чанки добавляются, курс
   скипается, `get_course_by_doc_name`). Различать по папке:
   - то же `doc_name` в ДРУГОЙ ролевой папке → копия (текущее поведение №1);
   - то же `doc_name` в ТОЙ ЖЕ папке (новый file_id) → новая версия: удалить
     старые чанки этого документа этой папки, ре-ингест, `questions_json`
     курса НЕ трогать (правки HR из №3 не терять; перегенерация — только
     вручную по команде, если клиент попросит).
   Для этого чанкам нужна привязка к документу: добавить в `normalised`
   поля `doc_name` и `folder_id` (сейчас только text/heading/section/roles/audience).
5. **Удаление чанков при удалении файла.** Поллер per-folder сравнивает listing
   с `processed_files` по folder_id → пропавшие file_id → удалить чанки
   (по doc_name+folder_id) и строки embeddings, снять запись из processed_files,
   курс пометить архивным (новая колонка `courses.archived_at`; активную сессию
   сотрудника не убивать — вопросы живут в questions_json).
   - **Legacy-ограничение:** исходные 842 чанка не привязаны к file_id
     (загружены до пайплайна) — замена/удаление работает только для документов,
     заливавшихся через пайплайн. Зафиксировать в отчёте клиенту.
   - Embeddings выровнены с чанками ПО ИНДЕКСУ: удаление = маска на обе
     структуры одним проходом, бэкап `*.bak` (паттерн `scripts/dedup_index.py`),
     запись через tmp + `os.replace` (сейчас json/npy пишутся на живую —
     рестарт посреди записи убьёт индекс), затем `chunks, embeddings = load_index()`.

## FEATURE 5 — Геймификация (16 ч / 32 000 ₽)

1. **«Благодарность» после сдачи экзамена** (passed = ≥70%, порог уже в
   `_finish_phase`): пост в Ленту новостей через `log.blogpost.add`
   (метод в выжимке подтверждён, ~строка 39479: для адресации нужны ID
   пользователей). Спец-тип «Благодарность с медалью» через REST может быть
   недоступен — тогда обычный пост с поздравлением и упоминанием; проверить
   формат DEST/SPERM в выжимке на этапе PRP. ФИО — из `employees` (№2).
2. **Еженедельный рейтинг в ленте:** фоновая задача по образцу `_disk_poll_loop`
   (asyncio, сон до понедельника 10:00 МСК), агрегат из `sessions` за неделю
   (завершившие, топ по score_exam+score_basic) → `log.blogpost.add`.
   - Идемпотентность: рестарт сервера не должен задваивать пост — хранить
     метку последней публикации (таблица `meta` key-value или строка в SQLite).
   - Публиковать только ЛУЧШИХ (топ-5), не антирейтинг.

## OTHER CONSIDERATIONS

- **Порядок:** №2 → №3 (нужна employees) → №4 → №5. Один PRP = одна доработка.
- **Сеть флапает** (WSL2 → portal.becar.ru / OpenAI): сохранять retry-паттерны
  (_send 5×backoff, timeout=20/max_retries=3 в rag.py). Живая проверка Bitrix-вызовов
  достоверна только с сервера/ngrok — из WSL возможны ложные таймауты.
- **Дедуп входящих** `_is_duplicate` (15с) уже глушит повторы — новые HR-команды
  получают его бесплатно, но двухшаговая правка №3 шлёт РАЗНЫЕ тексты — конфликтов нет.
- **.env новые ключи:** `WATCH_DEPARTMENT_IDS`; обновить `.env.example` с комментариями.
- **Все тексты пользователю — русские** (UTF-8), тон как в существующих сообщениях (ты-форма).
- **onboarding.db живая** — только аддитивные миграции (ALTER/CREATE IF NOT EXISTS
  + сидинг), никаких DROP/пересозданий; перед №4 (мутации индекса) — бэкап
  chunks_cache.json/embeddings_cache.npy обязателен.
- **Неопределённости, найденные на ресёрче (в PRP пометить как проверяемые живьём):**
  1) может ли imbot писать пользователю, который ни разу не открывал диалог с ботом
     (автостарт №2); 2) доступность OnUserAdd простому вебхуку; 3) CHAT_ID vs
     DIALOG_ID для im.disk.file.commit (№4); 4) «Благодарность» как спец-пост
     vs обычный пост в ленте (№5); 5) PDF — делать или нет (расхождение
     сметы и planning.md).
- Вопросы «как назначить конкретный курс сотруднику» (сейчас `active_courses[0]`)
  и «масштаб на франшизы» — НЕ в этих доработках, не расширять скоуп.
